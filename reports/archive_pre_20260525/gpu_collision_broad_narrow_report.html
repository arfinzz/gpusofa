GPU Collision Detection Report: Current Surgical Dense-Grid Path

Updated report for the current SOFA v25.12 + SofaGpuCollision implementation after removing the redundant object-level GPU AABB broad-phase work and moving primitive candidate generation into a GPU dense-grid path inside the narrow phase.

Workspace: C:\Users\arfin\Desktop\GPU SOFA Environment: WSL2 wsl-gpu-proj SOFA: v25.12 GPU: NVIDIA GeForce GTX 1650 Ti Mode: detection benchmark, no response Report date: 2026-05-07

1. Executive Summary

The broad phase has not been deleted from SOFA's pipeline, because CollisionPipeline still requires a broad-phase component to produce object-level collision model pairs. What changed is more important: the old GPU root-AABB culling kernel is disabled by default for the surgical two-object case.

For the target scene shape, one tissue object and one blade/tool object, the broad phase now acts as a small compatibility pass that emits the valid tissue/tool object pair. The actual broad filtering that matters for collision detection is now the GPU dense 3D grid inside GpuCollisionNarrowPhase.

Current Truth

  • Object-level GPU AABB culling: disabled by default with useObjectAabbCulling=false.
  • SOFA broad phase: still present, emits tissue/tool model pair.
  • Primitive candidate generation: GPU dense grid.
  • Duplicate pair removal: enabled with sort + unique.
  • Detection-only D2H: counters only, 16 bytes per step in verified benchmark.
  • Remaining bottleneck: CPU-staged triangle upload, 512480 bytes per step.

3. Broad Phase: What Was Removed and What Remains

The earlier report described a GPU root-AABB broad phase. That code still exists for general scenes, but it is no longer the default for the surgical two-object path. The current constructor default is: 

d_useObjectAabbCulling = false

With that setting, GpuCollisionBroadPhase loops over the registered collision models, applies SOFA's intersector compatibility checks, and emits the valid model pairs. For one tissue and one blade this becomes exactly one object pair.

Broad-phase item Current behavior Why
Object-level GPU AABB culling Disabled by default One tissue and one blade means object-level culling adds latency but does not reject anything useful.
SOFA broad-phase component Still required CollisionPipeline expects a broad phase to feed the narrow phase.
Broad output Usually one pair: tissue model vs blade model The actual primitive filtering is now done in the dense grid.
Measured broad GPU kernel 0.000000 ms No broad CUDA kernel is launched in the default surgical path.
Precise wording: broad phase is not totally removed from SOFA. The redundant object-level GPU broad-phase collision detection has been bypassed by default. The real broad filtering is now primitive-level dense-grid candidate generation inside the narrow phase.

4. Dense Grid Concept

The scene is divided into one shared 3D grid. There are not two separate grids. Each cell stores two lists: tissue triangle ids and tool triangle ids. If a tissue triangle and a tool triangle land in the same cell, they become a candidate pair.

Figure 2. One global 3D grid. Every cell stores two triangle-id lists: tissue ids and tool ids. A triangle can overlap multiple cells, which is why duplicate candidate pairs must be removed.

4.1 Grid Data Structures

struct DeviceCellBucket
{
    uint32_t tissueCount;
    uint32_t toolCount;
};

DeviceCellBucket* grid;
uint32_t* cellTissueIds;  // cellId * maxTissueTrianglesPerCell + localIndex
uint32_t* cellToolIds;    // cellId * maxToolTrianglesPerCell + localIndex

5.1 Candidate Generation Per Cell

// One CUDA block owns one cell.
cellId = blockIdx.x
x = min(grid[cellId].tissueCount, maxTissueTrianglesPerCell)
y = min(grid[cellId].toolCount, maxToolTrianglesPerCell)
totalPairs = x * y

for localPair = threadIdx.x; localPair < totalPairs; localPair += blockDim.x:
    tissueLocal = localPair / y
    toolLocal   = localPair % y
    tissueId = cellTissueIds[cellId * maxTissuePerCell + tissueLocal]
    toolId   = cellToolIds[cellId * maxToolPerCell + toolLocal]
    candidatePairs[atomicAdd(candidateCount, 1)] = encode(tissueId, toolId)

5.2 Duplicate Removal

Duplicate removal is necessary because a triangle AABB can overlap multiple grid cells. The same tissue/tool triangle pair can therefore be emitted by more than one cell. The current implementation deduplicates with: 

thrust::sort(candidatePairs, candidatePairs + usedCandidateCount)
uniqueEnd = thrust::unique(candidatePairs, candidatePairs + usedCandidateCount)
exactCandidateCount = uniqueEnd - candidatePairs

In the verified one tissue / one blade benchmark:

  • raw candidate pairs: 2304
  • unique candidate pairs after dedup: 624
  • exact contacts emitted: 104

5.3 Exact Contact Kernel

The exact kernel runs one thread per unique candidate pair. Each thread decodes one uint64_t pair, loads one tissue triangle and one tool triangle, and runs the existing triangle-triangle Separating Axis Theorem test. Intersecting pairs write one compact DeviceExactContact record with an atomic contact counter.

6. Narrow-Phase Call Graph

The narrow phase is not just one CUDA kernel. It is a SOFA callback layer, a CPU staging layer, a persistent CUDA workspace layer, and then a sequence of GPU kernels/device operations. The current surgical path is selected when both collision models can be interpreted as CudaTriangleCollisionModel and useDenseGrid=true.

8. Exact Contact Kernel Creation and Execution

The exact contact kernel is not launched over all tissue triangles times all tool triangles in the dense-grid path. It is launched only after candidate generation and deduplication. Therefore, exactCandidateCount determines the CUDA grid size. 

const auto contactBlocks =
    static_cast<uint32_t>((exactCandidateCount + threadCount - 1) / threadCount);

exactDenseGridContactKernel<<<contactBlocks, 256>>>(
    deviceTissueTriangles,
    deviceToolTriangles,
    deviceCandidatePairs,
    exactCandidateCount,
    deviceContacts,
    config.maxCandidatePairs,
    deviceContactCount,
    deviceOverflowCount);
Figure 5. Exact contact kernel mapping. One CUDA thread owns one unique candidate pair. Only intersecting pairs append a DeviceExactContact using an atomic counter.

8.1 Exact Kernel Per-Thread Logic

candidateIndex = blockIdx.x * blockDim.x + threadIdx.x
if candidateIndex >= candidateCount:
    return

candidatePair = candidatePairs[candidateIndex]
tissueTriangleId = candidatePair >> 32
toolTriangleId = candidatePair & 0xffffffff

DeviceExactContact exactContact
if exactTriangleIntersection(tissueTriangles[tissueTriangleId],
                             toolTriangles[toolTriangleId],
                             exactContact):
    outputIndex = atomicAdd(contactCount, 1)
    if outputIndex < maxContactCount:
        contacts[outputIndex] = exactContact
    else:
        atomicAdd(overflowCount, 1)

9. Exact Triangle Intersection Details

exactTriangleIntersection() is the device function called by the exact contact kernel. It uses a triangle-triangle Separating Axis Theorem style test. The function returns false as soon as it finds a separating axis. If no separating axis is found, it builds a compact contact record.

Figure 6. Exact triangle intersection flow. The function tests triangle normals and edge-cross axes. If all projections overlap, it creates a contact record from centroids and the best overlap axis.

9.1 Axes Tested

Axis source Count Code path Purpose

Second triangle normal 1 testSeparatingAxis(first, second, secondNormal, ...) Separates triangles by plane normal of second triangle.
Edge cross products 9 cross3(firstEdges[i], secondEdges[j]) Separates by pairwise edge axes.

9.2 Contact Record Contents

outContact.firstTriangleIndex  = first.triangleIndex
outContact.secondTriangleIndex = second.triangleIndex
outContact.pointOnFirst        = midpoint(firstCentroid, secondCentroid)
outContact.pointOnSecond       = midpoint(firstCentroid, secondCentroid)
outContact.normal              = bestAxis, oriented from first to second

9.3 Important Accuracy Note

This exact contact implementation is suitable as a current GPU detection milestone and benchmark target, but it is not a full IPC-style robust contact solver. It uses a compact SAT-style overlap/contact approximation. For surgical-grade fast tools, the next realism steps are swept tests, edge-edge and point-triangle CCD, persistent manifolds, and then a GPU response solver.

11. Detection-Only Mode vs SOFA Response Mode

Detection-Only Benchmark Mode

copyContactsToHost = false
  • GPU computes exact contacts.
  • Full DeviceExactContact[] stays on GPU.
  • CPU receives only counters for profiling and validation.
  • No SOFA DetectionOutput is published.
  • Correct for benchmarking detection and GPU residency.

SOFA Compatibility Response Mode

copyContactsToHost = true
  • GPU computes exact contacts.
  • Contacts copy back to CPU.
  • GpuCollisionNarrowPhase publishes SOFA detection outputs.
  • Required if using CPU/SOFA collision response.
  • Less GPU-resident, but compatible with existing SOFA response.
Important: the verified benchmark disables collision response. SOFA prints a ContactManager warning because response is intentionally absent. That warning is expected for this detection-only report.

12.1 Why CPU Is Still Faster Here

The implementation is good for the direction we want, but this benchmark does not yet measure the final GPU-resident architecture. It measures a transitional integration path: SOFA still owns the collision model at the CPU boundary, the plugin packs triangle records on the host, uploads all triangle records every step, launches several small kernels and device operations, synchronizes to read counters, and then returns to SOFA. For a small one-blade workload, that fixed overhead is larger than the actual triangle-triangle work.

The CPU path is not doing something conceptually better. It is simply mature, local, and cheap for this size: the data is already in host memory, ParallelBVHNarrowPhase is optimized, and the scene has only one tissue surface and one blade. The GPU path will start winning when the expensive parts stay resident on device and when the benchmark has enough contact work to amortize launch, synchronization, deduplication, and upload overhead.

Figure 8. Performance anatomy. The benchmark still pays transitional CPU/GPU integration costs. The target architecture removes those costs by keeping state, mappings, contacts, and response on GPU.

12.2 Bottleneck Diagnosis

Bottleneck Current evidence Why it hurts this benchmark Fix required for speedup
Per-step H2D triangle upload 512480 bytes/step The benchmark uploads the complete tissue and blade triangle records every step before any GPU work starts. Keep positions, triangle topology, AABBs, and mapped collision geometry resident on GPU.
Dense grid launches over all cells 64 * 8 * 64 = 32768 cells One block per cell is simple and parallel, but most cells are empty for one blade touching a local patch. Compact active cells, or switch candidate generation to a sorted sparse hash list.
Duplicate removal cost 2304 raw pairs become 624 unique pairs Sorting a few thousand pairs can cost more than simply testing them on CPU for this tiny case. Use active-cell compaction plus canonical owner-cell rules, or keep dedup only for larger/contact-response runs.
Kernel launch and synchronization overhead clear, AABB, insert, pair generation, sort/unique, exact contacts, counter copies The useful exact work is small, so fixed GPU orchestration overhead dominates the step time. Fuse kernels where practical and capture the stable step with CUDA graphs.
Only detection is GPU-resident copyContactsToHost=false leaves records on GPU, but SOFA still drives the frame The benchmark proves low D2H for detection, not full GPU simulation throughput. Move FEM state, mappings, solver, contact metadata, and final response onto the GPU path.
CPU baseline is strong for small scenes ParallelBVHNarrowPhase with host-resident data For one blade and one modest tissue surface, CPU cache locality and mature SOFA code are hard to beat. Benchmark larger/deeper contact scenes after removing residency and launch overhead.

So the conclusion is not that the GPU implementation is bad. The conclusion is sharper: the current dense-grid narrow phase is architecturally useful and correctness-friendly, but the benchmark is too small and too CPU-integrated to expose a speedup. The next speed milestone is not another triangle test; it is eliminating the per-step upload, avoiding empty-cell work, reducing synchronization, and benchmarking after the collision geometry is genuinely device-owned.

13. Memory Residency and Allocation Behavior

The dense-grid backend uses a persistent DenseGridWorkspace. It grows buffers on demand and then reuses them across frames. In the verified benchmark, the first GPU row allocated 138247948 bytes because the workspace had to be created for the larger per-cell capacities. After that, allocation was 0 bytes per step, and the measured post-warmup average was 0.

14. Mapping and Data Ownership

In the benchmark scenes, the collision surfaces are direct CudaVec3f triangle surfaces, so there is no separate render mesh or simulation-to-collision mapping. In the broader surgical architecture, the intended mapping is still: 

simulation tet mesh on GPU
    -> GPU collision surface / collision tet mesh
    -> GPU render mesh
    -> GPU dense-grid detection
    -> GPU response later
Figure 9. Intended GPU-resident mapping architecture. The current benchmark uses direct collision surfaces; future tissue simulation should keep mapping outputs on the GPU before dense-grid detection.

15. Fallback and Correctness Guards

  • If dense-grid capacity overflows, the narrow phase rejects the grid result and can fall back for correctness.
  • If models are unsupported or not CUDA triangle models, the legacy SOFA/BVH path remains available.
  • allowCPUFallback=true keeps the scene from failing hard during unsupported combinations.
  • Overflow count is exported and was verified as 0 in the final benchmark.
  • Dedup is enabled by default with deduplicatePairs=true.

17. Final Takeaways

  • The redundant object-level GPU AABB broad phase is no longer active for the surgical two-object path.
  • The SOFA broad phase remains only as a contract to emit the tissue/tool object pair.
  • The dense 3D grid inside narrow phase is now the real primitive-level broad filter.
  • Candidate duplicate removal is implemented and verified.
  • Detection-only GPU mode avoids full contact D2H transfer; only counters copy back.
  • The remaining major transfer is CPU-staged triangle H2D upload.
  • For small one-tool scenes, CPU can still be faster because the GPU path has staging, kernel launch, sort, and synchronization overhead.
  • The next performance milestone is direct device-buffer integration for SOFA CUDA collision geometry and later GPU response consumption of the contact buffer.
